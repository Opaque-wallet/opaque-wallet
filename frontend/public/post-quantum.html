Each payer uses it to make a fresh one-time address that only your key can find, and announces it on ERC-5564's Announcer. Your wallet spots its own and sweeps them into your notes.

    From Alice's key to Alice's notes, in five steps.

    secp256k1 stealth addresses · ERC-5564 scheme 1

    A quantum computer reading old announcements recomputes every shared secret, and links each payment to its recipient.

    ML-KEM-768 · this scheme

    It can't. ML-KEM has no known quantum attack, so the announcements stay sealed, old ones included.

    Until Alice sweeps, Bob also holds the one-time account's keys: hash-based keys can't be tweaked the way elliptic-curve ones can. Her wallet sweeps as soon as the payment lands.

    Names · ENSv2 · Live on Sepolia

    A name no quantum computer can take.

    opaque.eth is held by PQNameController, the sole holder of every role on the name, and it acts only on a FORS+C signature. Under it, yourname.opaque.eth can be claimed only by a post-quantum account. ENSv2's own UniversalResolver walks the tree and returns that account, so paying a name pays a key a quantum computer can't take.

    • Every write is signed with FORS+C: the target, the exact calldata and a deadline, at the key's use count in PQKeyRegistry, so each signature works once. ECDSA writes revert, the original owner's setResolver included
    • Subnames for PQ accounts only: OpaqueNames, opaque.eth's subregistry, checks the claimant's code hash. One name per account, and release() frees it
    • Rotation built in: a key signs up to 32 times, then the registry hands the name to the key committed next
    • Claiming a name publishes your stealth key in the same signature, so payments to it land at one-time addresses. Lookups go through anon-rpc

    Swap · Uniswap v4 hook · EIP-8141 devnet

    A pool only post-quantum accounts can trade in.

    PQPoolHook is a Uniswap v4 hook that admits only accounts whose one authority is a FORS+C key. It checks every swap, every liquidity change and every donation, so a cracked ECDSA key can't touch the pool, and a position moved to an ECDSA wallet freezes instead of leaving. It's live on Ethereum's EIP-8141 devnet, where accounts validate themselves: no bundler, no paymaster.

    • 0.001 ETH → 1.974316 pqUSD: a post-quantum account's swap in the pool, exactly the quote. See the swap
    • The same swap from an ECDSA wallet, through the same router, reverts with the hook's NotPostQuantum
    • One FORS-signed transaction, four frames: deploy the hook, admit the account, open ETH/pqUSD under the hook and add its liquidity. See the setup
    • Hook 0x3B28…caa0: its last bits are v4's permission flags, so the address itself says which calls it checks

    Liquidity guard · Any wallet · Live on Sepolia

    Still on ECDSA? Add a post-quantum key.

    PQGuardHook protects liquidity anyone provides, ECDSA wallets included. Register a FORS+C key once, with an ordinary transaction. From then on, every removal from your position, fees too, needs that key's signature over the exact amount, a recipient and a deadline. The hook pays the recipient it names itself, so whoever cracks your ECDSA key can't take the liquidity, or redirect a removal you sign.

    • The guard key, registered in PQKeyRegistry by an ordinary ECDSA wallet. See it

    Why now

    Moving later means moving in a hurry.

    Every ECDSA signature ever published reveals its public key, so the day a large quantum computer exists, those accounts can be taken. The cheapest time to move is before anyone has to.

    • Hash-based, not lattice-based. FORS+C rests on the hash function alone, the most conservative assumption there is.
    • Few-time keys, rotated for you. Each key signs a set number of times, and the wallet hands over to the next one before it runs out.
    • Bigger signatures. About 9 KB instead of 65 bytes, which costs more calldata. The verifier is tuned to fit the public mempool's budget anyway.
    • Testnets first. Sepolia and the devnet today, mainnet after an audit. The code is open (Apache-2.0).
